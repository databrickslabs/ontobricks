# OntoBricks 0.8 Upgrade Guide Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Verify the supported 0.7.x-to-0.8.0 Lakebase migration and publish an accurate English guide for fresh installs and in-place upgrades.

**Architecture:** Keep the standalone SQL migration as the auditable DBA path and the existing Lakebase bootstrap as the automatic deployment path. Add static contract tests to prevent drift between the canonical schema, migration SQL, preflight expectations, and updater; document both supported workflows without introducing a second migration mechanism.

**Tech Stack:** PostgreSQL/psql, Bash, Python/pytest, Databricks Asset Bundles, Markdown.

## Global Constraints

- Target release is exactly `0.8.0`.
- Supported guide paths are fresh 0.8.0 installation and in-place upgrade from 0.7.x.
- The 0.8 registry migration must be additive, transactional, idempotent, and preserve 0.7 behavior with `mcp_policy = '{}'::jsonb`.
- The normal deployment path remains `scripts/bootstrap/lakebase-perms.sh`; `scripts/migrations/upgrade_0.7_to_0.8.sql` remains the manual DBA path.
- Do not run a live deployment as part of this change.
- Run `uv run --frozen pytest -q -m "not scenario"` after all changes.

The guide must instruct operators to:

- check out the 0.8.0 source and run `uv sync --frozen --extra lakebase`;

- use `scripts/update-deployed-app.sh <UI_APP_NAME> <MCP_APP_NAME>` for an in-place 0.7.x upgrade;
- use `psql "$PGURL" -v reg_schema=<schema> -f scripts/migrations/upgrade_0.7_to_0.8.sql` only as the alternative manual migration;
- verify `domains.mcp_policy`, both app states, resource bindings, `/healthz`, and the MCP server;
- roll back application code without dropping the additive column.
