# OntoBricks 0.8 Deployment and Upgrade Design

## Scope

Document and verify two supported paths:

1. A fresh OntoBricks 0.8.0 installation.
2. An in-place upgrade from OntoBricks 0.7.x to 0.8.0.

Earlier releases are outside this guide's supported upgrade scope. Existing
sequential migration scripts remain available but will not be presented as a
validated direct upgrade path to 0.8.

## Upgrade Strategy

Keep `scripts/migrations/upgrade_0.7_to_0.8.sql` as the explicit, auditable SQL
migration. It adds the only 0.8 registry DDL change,
`domains.mcp_policy`, with an empty JSON object default that preserves 0.7
behavior. The script remains transactional and idempotent.

The normal deployment path continues to use
`scripts/bootstrap/lakebase-perms.sh`, which checks migration state and applies
the equivalent DDL only when needed. This avoids replaying owner-only DDL on an
already-current registry. The standalone SQL file is the manual DBA path, not
a second mandatory deployment step.

## Documentation

Create `update_to_0.8.md` at the repository root in English. It will contain:

- prerequisites and compatibility scope;
- backup and configuration checks;
- fresh 0.8.0 installation steps;
- in-place 0.7.x upgrade steps using `scripts/update-deployed-app.sh`;
- automatic and manual SQL migration alternatives;
- UI and MCP deployment behavior;
- post-upgrade schema, app health, resource-binding, and MCP checks;
- troubleshooting and rollback guidance.

Existing deployment documentation will be corrected only where it contradicts
the live scripts or the new upgrade guide. The root guide will link to the
detailed deployment documentation rather than duplicate its full reference.

## Verification

Add or update focused tests that ensure:

- the 0.7-to-0.8 migration contains the canonical `mcp_policy` definition;
- the deployment bootstrap and preflight expect the same 0.8 schema change;
- documentation points to current script names and behavior.

Run the mandatory non-scenario suite:

`uv run --frozen pytest -q -m "not scenario"`

Run deployment-safe static checks where available without deploying to a live
workspace. A live deployment is not part of this change.

## Failure and Rollback Behavior

The SQL migration uses `ON_ERROR_STOP` and a transaction, so a failed DDL or
sanity check rolls back the schema change. Application deployment should only
proceed after a registry backup. Rollback primarily restores the previous
application version; the additive `mcp_policy` column may remain because 0.7
ignores it. Dropping the column is unnecessary and would discard 0.8 policy
configuration.
