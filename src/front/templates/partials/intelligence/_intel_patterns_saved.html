Patterns find entities that look alike: the same kind of connections and similar characteristics. Think of them as typical profiles discovered automatically in your data, without writing a single rule.

Energy example. Among 10 000 customers, Patterns might find that 3 200 have a residential contract, a smart meter and high consumption, while 900 have a business contract with several meters. Each of these groups is a pattern, and you can open the list of customers behind it.

Step 1: Pick what you want to profile

Choose one type of entity, for example Customer. Every customer will be described and compared with the others.

Step 2: Look around each one

For each customer, OntoBricks follows the relationships a few steps away (the Hops setting): its contracts, the tariff of each contract, the sites it owns, the meters installed there, and so on.

Step 3: Describe each one in simple terms

Exact values would make every customer unique, so details are simplified: numbers become ranges (a consumption of 4 812 kWh becomes high), short lists of categories are kept (residential, business), and unique identifiers such as emails or contract numbers are ignored.

Step 4: Group the look-alikes

Customers with the same description fall into the same pattern. The number of customers in a pattern is its support. Patterns that are too rare (below Min support) are hidden.

Step 5: Simplify automatically when needed

If almost every customer is still unique, OntoBricks drops the finer details step by step (first the neighbours’ characteristics, then all characteristics) until at least half of the customers belong to a pattern. The diagram badge tells you which level was used.

Settings in plain words
  • Hops: how far to look around each entity (2–3 is usually enough).
  • Numeric bins: how finely numbers are split into ranges (more bins means stricter look-alikes).
  • Min support: the smallest group worth showing.
  • Refine top-N: merges near-identical top patterns that differ only by counts (0 = off).
What to do with the results
  • Open a run to see each pattern drawn as a diagram (the entity on the left, then 1 hop, 2 hops, …).
  • Hover a box to highlight its path; hover a link or a badge for an explanation.
  • Matching entities lists the customers behind a pattern, with links to Graph Explorer.
  • Typical uses: segment customers, spot unusual set-ups (rare patterns), check data quality.
Technical details
1. Choose the anchor type

Detect starts from one ontology class (for example Customer or Claim). Every instance of that type becomes an anchor. Neighbours of other types are still walked and recorded in each anchor’s signature.

2. Expand the neighbourhood (Hops)

From each anchor the job walks the graph up to the configured hop depth (default 3, range 1–5), following relationships in both directions (out and in). At every hop it records the parent type, the predicate (via), the child type, and the direction.

3. Bin attributes (Numeric bins)

Exact values would make almost every entity unique, so attributes on the anchor and on typed neighbours are normalised:

  • Numeric values are cut into quantile buckets (default 8 bins → labels like bin 1/8 … bin 8/8).
  • Categorical values are kept as-is when the property has at most 20 distinct values in the graph.
  • Identifier-like properties (emails, UUIDs, free text — more than 20 distinct values) are ignored so they cannot shatter patterns.
4. Build canonical tokens

Each anchor’s neighbourhood becomes a sorted bag of tokens, for example:

  • Structure — hop | relation | neighbour-type | direction
  • Anchor attributes — 0 || anchor-type | self | property | bin
  • Neighbour attributes — hop | relation | type | direction | property | bin
5. Adaptive detail levels

If the full token set is too specific (almost every anchor unique), the job walks down four abstraction levels until patterns cover at least 50 % of the anchors:

  1. full — structure, multiplicities, and all binned attributes.
  2. neighbour — ignore multiplicities; neighbour attributes only at 1 hop.
  3. own — multi-hop structure, but attributes only on the anchor.
  4. structure — typed paths only; no attributes.
6. Hash into a pattern id

Tokens are sorted and hashed (MD5). Anchors that produce the same hash share one pattern. Support is the number of anchors in that group.

7. Optional refine (Refine top-N)

When Refine top-N is greater than 0, the job inspects the top N patterns by support and collapses near-duplicates that share the same typed paths but differ only by small multiplicity differences into unified motif templates. 0 leaves refine off.

8. Filter by Min support

Patterns with fewer anchors than Min support (default 3) are dropped. Raise it to keep only dominant shapes; lower it to surface rare ones.

Execution and storage

Detection runs as a Databricks job on the Knowledge Graph snapshot, not in the browser. Each Detect run is saved automatically to Unity Catalog; open a card to revisit it.
