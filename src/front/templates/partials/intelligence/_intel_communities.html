Communities find clusters: groups of entities that are much more connected to each other than to the rest of the graph, a bit like neighbourhoods in a city. Nobody defines the groups up front; they emerge from the links in your data.

Energy example. Sites, meters and customers fed by the same substation are heavily linked together, and only loosely linked to other regions. Community detection puts each of these areas into its own community, for example North grid, City centre and South grid, without anyone listing which site belongs where.

Using it, step by step
  1. Detect: runs the grouping on Databricks. Optionally limit it to one entity type (for example only Sites).
  2. Preview: browse the biggest communities, their size, and click one to list its members.
  3. Read the quality score (modularity): the higher it is, the more clearly the groups stand apart. Use it to compare runs, not as a pass/fail.
  4. Materialize: writes the communities into the knowledge graph so Graph Explorer can colour and collapse them. Clear graph removes them again.
Typical uses
  • Find natural operating areas (grid zones, field-team territories).
  • Spot entities that bridge two areas (a site shared by two networks), often worth a check.
  • Isolate small disconnected islands that may reveal missing links in the data.
Patterns or Communities?
  • Patterns answer “who looks alike?”: similar profiles, even if they are never connected.
  • Communities answer “who is connected together?”: clusters of linked entities, whatever their profile.
Technical details
1. Build the undirected edge set

From the Knowledge Graph …_data snapshot, the job builds an undirected neighbour list (entity–entity edges only). Optionally you can Scope the run to one ontology class; that filters which nodes are considered for community membership while still using the graph’s relationship structure.

2. Label propagation (semi-synchronous LPA)

The only algorithm in v1 is label propagation in portable SQL (Louvain is not practical in pure SQL on serverless compute):

  • Init — every node starts with its own label (itself).
  • Iterate — each step, a node adopts the most frequent label among its neighbours, counting its own current label as one vote. Ties break on the smallest label (deterministic).
  • Semi-synchronous — only half of the nodes update each iteration (parity of md5(node)). That avoids the classic two-colour oscillation of synchronous LPA on bipartite graphs (Customer → Order → Product).
  • Stop — when labels stop changing over a full parity cycle, or change falls below a tiny threshold, or after a max iteration cap (default 30). Unconverged runs are flagged, not failed.
3. Rank communities by size

Nodes that share a label form a community. Communities are ranked by size (descending) into dense integer ids (c-1, c-2, …) used everywhere in the UI and when materializing to the graph.

4. Quality signal (modularity)

The job reports modularity Q = Σ_c (L_c / m − (D_c / 2m)²): how much denser the intra-community edges are than a random partition with the same degrees. Higher is better; it is a summary metric, not a hard filter.

5. Preview (bounded)

The UI never downloads every member. Preview samples the top communities by size (capped node/edge counts), shows KPIs (clusters, nodes, edges, size stats, modularity), and loads members on demand when you click a cluster (paged “Load more”).

6. Materialize into the graph

Materialize writes the last Detect run into the triple store as cluster membership (and cluster metadata) so Graph Explorer can colour and collapse communities. That is a separate background task. Detect alone only updates the Delta preview tables; Clear graph removes the materialized partition without deleting the last Detect preview.

How this differs from Patterns
  • Communities — global connectivity partition; labels hop through the graph.
  • Patterns — recurring neighbourhood signatures rooted at one entity type (attributes + typed multi-hop shapes).
