Lakehouse

Unity Catalog Delta tables for the triple store — no separate graph database to provision

Loading Lakehouse configuration…
How it works

With Lakehouse selected as the graph backend, OntoBricks stores triples directly in governed Delta tables in Unity Catalog. The Registry catalog and schema (Settings → Registry) define where all triple-store objects live for every domain.

Pick a dedicated SQL Warehouse on the SQL Warehouse tab for Lakehouse graph queries and builds. When unset, the global warehouse from Settings → Databricks is used. After mapping is ready, run Knowledge Graph → Build to create the R2RML VIEW and materialize the _data Delta table.

Used only when Lakehouse is the graph backend — graph queries, health probes, and Lakehouse builds run against this warehouse. Click Apply to persist the selection in the registry.

    How long a DRAFT single-editor lock survives with no keep-alive (a crashed / closed tab) before another user can reclaim it. The editor's browser auto-renews while open. Set to 0 to disable the lease (a lock is then held until the editor closes the domain or an admin force-unlocks it).
    Graph analytics runs entirely in a serverless Databricks job, which computes counts, average degree, density, degree centrality, the entity-type profiles, PageRank, the clustering coefficient and the component count exactly, plus betweenness and closeness as sampled estimates. This is the only way analytics runs, so leaving it off disables the Analytics page. Requires the Databricks bundle to have been deployed, so that the job exists, and the domain to have been built at least once. The job reads the mapped-triples snapshot every Build materialises, so it works the same on the Delta engine, on Lakebase in either mode, and on Neo4j. When a prerequisite is missing the Analytics page says which one rather than falling back to a different calculation. Runs take minutes rather than seconds.
